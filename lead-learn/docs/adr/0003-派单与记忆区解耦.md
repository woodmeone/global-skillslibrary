# ADR-0003 · 派单落在工作区，与 recall 记忆区解耦

- 日期：2026-11-24
- 状态：已采纳
- 取代：`paths.py` 原「AGENT → `<RECALL>/<agent>/longterm/dispatch`」三档

## 背景

原设计：派单目录三档优先级

```
1. LEAD_LEARN_DISPATCH  显式指定
2. LEAD_LEARN_AGENT → <RECALL>/<agent>/longterm/dispatch
3. 都不设 → <HOME>/dispatch
```

第 2 档让派单文件住进了 recall 记忆区。当时理由是「跟着记忆区搬家、不依赖项目路径、
文件计数直接变成进度指示器」。

实际跑了几天，暴露出三个问题：

1. **语义错位。** recall 的 `longterm` 是「长期内容」——装判据、花名册、汇总，
   都是下次还要用的东西。派单文件是**这轮的待办**，学完就删。把过程状态放进长期记忆，
   等于把草稿夹进档案盒。

2. **搬家时机不同，必然错位。** 记忆区跟 `~/.midnight` 走（跟用户账户），
   工作区跟盘符走。两者不是同一次搬迁，路径迟早对不上。

3. **skill 与派单者绑死。** `LEAD_LEARN_AGENT` 的存在让 skill 必须知道
   "recall 在哪、谁在派单"。换个派单者（或没有 recall 的环境），整条链路要重配。

## 决策与取舍

**派单目录固定在工作区：`<HOME>/dispatch`。** `AGENT` 保留，但只用于两件事：
核盘面、在各 agent 的 `LONGTERM.md` 留一行指路。**它不再决定落盘位置。**

```
LEAD_LEARN_DISPATCH  显式指定（仍是最高优先，没动）
<HOME>/dispatch      默认，且这是唯一的默认
```

放弃的方案：

| 方案 | 为什么不选 |
|---|---|
| 保留三档，只把第 2 档改成「软链进记忆区」 | 软链会制造第二个可写真相源，违反 git-native-sop 不变量 1 |
| 派单留记忆区，加一个 `--workdir` 开关 | 默认值仍会让人踩坑；默认应该是对的，不是可切换的 |
| 完全不碰记忆区（连 LONGTERM 登记也不要） | 那就少了「索引没写等于没建」这道防丢机制，agent 会不知道有派单 |

## 后果

- **好**：素材、state、staged 稿、派单、日志全在一个工作区，一次备份带走全部；
  没有 recall 也能完整跑；skill 不再知道任何人的记忆区在哪。
- **好**：记忆区只剩 `criteria` / `roster` / `roundup`——**每一份都是「下次还要用」的**，
  开机清单不再被一堆 `staging` 文件占位。
- **坏**：进度指示器从「dispatch 目录里的文件数」变成「`dispatch.py status` 的输出」。
  少了一眼看出的便利，换来的是语义正确。
- **迁移成本**：已执行——13 个派单文件从
  `<RECALL>/lead/longterm/dispatch` 移到 `<HOME>/dispatch`，用 move 不是 copy（不留第二份）。

## 判据（下次判断某样东西该放哪，用这条）

> **这轮的待办 → 工作区；下次还要用的判断 → 记忆区。**

- 派单队列、pipeline-state、日志 → 工作区（过程）
- 分流判据、花名册、学习汇总、ADR → 记忆区 / 仓库（沉淀）

拿不准时问一句：**学完/跑完之后，这份东西还该留着吗？**
该留 = 记忆区或仓库；该删 = 工作区。
