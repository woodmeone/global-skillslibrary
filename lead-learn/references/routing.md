## 三条实测踩过的错

上一版把分流写成了脚本 `route_to_agents.py`，三处硬伤：

| 错 | 现象 | 根因 |
|---|---|---|
| **词表漏人** | 「一图看我20年的运营功力」永远不会派给量量 | `ROUTES` 字典里根本没有 `liangliang`。谁不在表里，谁永远不赢 |
| **只留一个赢家** | 那条明明横跨流量/变现/成交，只派给了商商 | `best = max(scores)`。一行代码把多选题压成单选题 |
| **字面计数看不懂语义** | 「运营」出现 20+ 次，商商 40 分，其余全 0 | `text.count(kw)`。数得出词频，数不出这段讲的是漏斗还是条款 |

**结论：分流不写脚本打分。** 判断在人这里，一次一条。脚本只做机械活——扫花名册、列稿子、落文件、核盘面。

## 判法

### 第一步：先判「它在讲什么」，不判「它像谁」

顺序反了就会按词面分流。

1. 看标题 —— 多数标题已经说明了主题（「谈判学案例」→ 谈判）
2. 看简介前 300 字 —— 确认在教方法、在抒情、还是在演剧情
3. **只在判不出归属时才读正文**。读正文是判归属，不是判质量

`dispatch.py list 80` 直接给出标题 + 前 80 字，够判多数条目。

### 第二步：一条材料可以归多人

**「可以归几个」是这道题的核心。** 判据一句话：

> 这条材料讲的事，是不是**每个人自己的活**？不是问「像不像他的领域」。

例子——「一图看我20年的运营功力」讲互联网运营四件事（用户/产品/内容/活动）：

| 角色 | 判不判 | 为什么 |
|---|---|---|
| 量量 | ✅ | 用户画像、内容矩阵、渠道因地制宜——就是「注意力为什么被拿走」 |
| 商商 | ✅ | 分层、投产比、转化路径、定价感知——就是「卖」 |
| 贸贸 | ✅ | 活动机制、二次传播、成交那一刻的摩擦——就是「谈成一单」的外围 |
| 面美 | ❌ | 通篇没讲画面。别因为「设计」出现在附近就塞过去 |

三个 ✅，派三个人。**不挑最像的那一个。**

反面例子：量量与商商容易混。分界是——**流量怎么来归量量，来了怎么变现归商商**。同一条材料两段都讲，就派两个人。

### 第三步：判不出就丢

不硬凑。判不出归属的材料，丢。

理由：塞给「最接近」的人，成本是那个角色花时间消化一堆不相关的东西，还会污染它的标签共现网。**比不派更糟。**

丢掉的三类（第一轮实测 15 份）：

| 类 | 例 | 判据 |
|---|---|---|
| 纯歌词 / 音乐 | 变装视频、清唱片段 | 转录出来是歌，没有可提炼的方法 |
| 民俗 / 宗教（ASR 乱码） | 玄天上帝 | ASR 出来是音节垃圾，连语义都没有 |
| 无信息量短片 | 20 字的感叹 | 字数太少，构不成一条内容 |

### 第四步：拿不准的单独列

`plan.json` 有 `undecided` 数组。判得出「它有价值」但判不出「值不值这个成本」的，放这里，交给人点头。

第一轮那 3 条长剧情（8 万字网文合集、世界观拆解、剧情片段）就在这里。

## 派单文件里写什么

`dispatch.py apply` 自动生成，一个角色一份：

```markdown
---
dispatched_by: lead-learn
dispatched_at: 2026-11-24T01:17:26
agent: liangliang
count: 3
---

## 1. <标题>

- 链接：<url>
- 平台：bilibili　key：`bili:BVxxx`
- 派给你的理由：<一句话：讲的是什么，为什么是他的活>
- 同时派给了：shangshang、贸贸（别替他们做，只取你要的）
```

三条硬规矩：

1. **不写正文，不附转录稿。** 角色要自己从头学——这是原话，不是偏好。
2. **`reason` 必写。** 只给链接不给理由，等于让它自己猜为什么派这活。
3. **`also` 必写。** 跨领域的材料标清还给了谁，免得两家重复劳动。

## 收活怎么验

**不听回报，看盘面实际变了什么。**

```powershell
python scripts/dispatch.py status                       # 剩几家没交、各剩几条
python scripts/dispatch.py verify --since 2026-11-24    # 各角色实际变了什么（增量）
```

三个判据：

1. `dispatch/` 里还有几**条**未划掉的条目 —— `status` 数条目，不数文件头（早期版本读 frontmatter 的 `count`，子智能体划掉条目不会改它，于是永远显示派单当天的数字）
2. 各角色 `longterm/` 在该日之后**新增/修改**了几个文件、`LONGTERM.md` 是否多了索引行（**索引没写等于没建**）
3. 各角色 `dailynote/` 是否多了今天的日记

回报说「收了 3 篇」但盘面没变，以盘面为准。

**`verify` 的 longterm 列必须是增量。** 早期版本数全量，开编这种 29 个文件基数的角色涨没涨看不出来，基数 1 的角色写一个也显示 "1"，跟没干活一样。
