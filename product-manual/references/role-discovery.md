# 角色与流程盘点（写手册前的第一步）

手册章节结构不能凭空编，必须从代码里读出来。按下面顺序盘，半小时能摸清一个中后台项目。

## 1. 先定角色，再定章节

角色数决定文档数。判断依据是**权限边界**，不是菜单数：

| 判断依据 | 结论 |
|---|---|
| 无需登录即可访问的页面 | 独立一份「用户侧」手册 |
| 登录后按 `role` 字段分流 | 每个 role 一份 |
| 同一 role 但数据范围不同（如商户 A 只看自己） | 合并为一份，在文中说明"你只看到自己" |

原则：**读者换人就要换文档**。一个商户看不懂管理员手册里的资金审批，硬塞在一起只会让两边都觉得文档在说别人的事。

## 2. 从代码里抓路由

Next.js App Router：

```bash
# 所有页面路由
find app -name "page.tsx" | sed 's|^app/||; s|/page.tsx$||; s|(.*)||'

# 后台导航项（章节顺序直接照这个排）
grep -o "label: '[^']*'" components/console/nav.tsx
```

导航组件里的 `admin: true` 标记就是角色分界线：商户手册只写 `admin: false` 的菜单，管理员手册写全部，并单独说明"商户看不到这 N 项是正常的"。

三个常见误判：

1. **把导航当功能清单**。详情页、表单弹窗、审核操作都在 page 里，不在导航里。要看 `app/**/[id]/page.tsx`。
2. **漏掉非导航入口**。支付链接 `/pay/[code]`、结算 `/checkout/[orderNo]` 是买家侧入口，不在任何后台导航里。
3. **漏掉 API 路由**。`app/api/**/route.ts` 决定了后台按钮背后的真实能力（如 `cron/payouts` 说明回款是异步的）。

## 3. 从领域层抓状态机

页面只显示状态，状态怎么流转在 `lib/domain/` 里：

```bash
grep -rn "STATUS_LABEL\|_LABEL =\|status:.*'pending'" lib/domain/ | head -40
```

找到形如 `const X_STATUS_LABEL = {...}` 的映射，就是该实体的全部状态。转成表格写进手册，读者比看界面更清楚自己在哪一步。

## 4. 从守卫抓权限

```bash
grep -rn "requireAdmin\|requireContext\|isPlatform" app/ lib/
```

`requireAdmin` = 管理员专属；`requireContext` = 登录即可；两者都不是 = 公开页面。这直接决定该写进哪份文档。

## 5. 输出一张盘点表

动手画章节前先填这张表，填不出来的格子就是要回代码里补的地方：

| 角色 | 入口路由 | 核心流程 | 状态机 | 不可逆操作 |
|---|---|---|---|---|
| 买家 | `/` `/search` `/cart` `/orders` | 浏览→加购→结算→付款→查单 | 待付款/已付款/已送达 | 无 |
| 商户 | `/console` | 开户→上架→发货→提现 | 草稿→审核中→已激活 | 提交审核 |
| 管理员 | `/console` | 审核→运营→审批→审计 | 审核中→通过/补件/拒绝 | 开户、放款、退款、下架 |

「不可逆操作」这一列别省。它是手册里最有价值的部分——读者真正需要的是"做之前该核对什么"，而不是"按钮在哪"。
